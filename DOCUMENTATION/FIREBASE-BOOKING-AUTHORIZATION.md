# Firebase booking authorization repair

The inspected source PATCH booking handler accepted any Authorization header beginning with Bearer without validating its Firebase ID token or loading/checking the related Peanut Account. Firebase Admin writes bypass client Firestore rules, so those rules do not establish ownership for this handler. Booking webhook authentication also fell back to a public hardcoded secret when no WEBHOOK_SECRET was configured. These are source findings; deployed function code identity has not been verified by this change.

The repair verifies Firebase ID tokens using the existing middleware, loads the UID-to-Peanut-account mapping and requires a real account before accessing a booking. A non-webhook caller must be the booking's performer or customer. The allowed update fields remain unchanged; finer payment/status authority still needs business-policy review. Properly signed operator-configured Booker/Festival webhooks retain their behavior. Missing webhook configuration or malformed signatures fail closed; no public default secret is used. No production credential was rotated, fetched or provisioned.

Six local HTTP regressions exercise the compiled Express router with in-memory Firebase mocks: invalid bearer-shaped tokens and foreign-party accounts cannot write; valid involved accounts and properly configured signed webhooks can; missing/default/malformed authentication cannot write. The suite is wired to the pinned Node 20.20.0/npm 10.8.2 functions CI lane. Local TypeScript build and all six tests pass on Node 22.23.2, so required-runtime CI qualification remains mandatory.

No Firebase database, function, security rule, storage object or deployment was changed by local verification. Before deploying this repair, identify the actual function owner/runtime, verify a non-public configured webhook secret through secure operator tooling, identify callers and demonstrate valid-token/party and webhook flows in a non-production environment. Do not rely on public health success to establish deployed authorization parity, and do not test writes against customer bookings as discovery.
